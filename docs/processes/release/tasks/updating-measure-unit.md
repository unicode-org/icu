# Updating MeasureUnit with new CLDR data

{: .no_toc }

## Contents

{: .no_toc .text-delta }

1. TOC
{:toc}

---

This document explains how to update the C++ and Java version of the `MeasureUnit`
class with new CLDR data.

This document applies to ICU 77 and later.
For older versions see [updating-measure-unit-old.md](updating-measure-unit-old.md).

## When to do this

Do this when CLDR adds, removes, or renames a unit. \
The ICU4J test `MeasureUnitTest.testCLDRUnitAvailability` fails when CLDR has a
unit that `MeasureUnit` has no constant for, for example:

```
MeasureUnitTest	testCLDRUnitAvailability	Failure	(MeasureUnitTest.java:3410) : Unit present in CLDR but not available via constant in MeasureUnit: speed-beaufort
```

The generator reads the list of units from the ICU4J data at runtime
(`MeasureUnit.getAvailable()`). \
So the new CLDR data must already be in ICU4J before you run it.
See step 12, "Transfer the ICU4C data to ICU4J", in
[CLDR-ICU integration](../../cldr-icu.md).

The list also includes every existing constant, so the generator doesn't remove one. \
If CLDR removes or renames a unit and its constant is `@draft`, remove the constant by hand
from `MeasureUnit.java` and from the tests that use it, such as `TestCompatible<version>()`,
before you run the generator (like `MIL` in CLDR 49).
A `@stable` constant must stay. For example, special code in the generator keeps
`METRIC_TON` as an alias of `TONNE`.

## Update `DRAFT_VERSION_SET`

Make sure `DRAFT_VERSION_SET` at top of
`./icu4j/main/common_tests/src/test/java/com/ibm/icu/dev/test/format/MeasureUnitGeneratorTest.java`
is set correctly. \
These are the ICU versions that have draft methods.
The generator uses this set, together with the `JAVA_VERSIONS` table in the same file,
to decide if each constant gets `@draft` or `@stable`.

* If CLDR adds units in this release, add the current ICU major version.
  New units get `@draft ICU <current version>`, and the version must be in the
  set so that they stay `@draft` the next time the generator runs.
* If the draft units of a version were promoted to stable (see
  [Promote draft APIs to stable](docs.md#promote-draft-apis-to-stable)),
  remove that version. \
  Otherwise the generator changes those constants back to `@draft`.

## Generate the code

The code is generated by running `MeasureUnitGeneratorTest.java` unit tests, which writes
generated code to various files.

1. With **maven** (command line):
   - Change folder to `{icuRoot}/icu4j`
   - run `mvn install -DskipTests -DskipITs`
   - run `mvn install -q -Dtest=MeasureUnitGeneratorTest -DgenerateMeasureUnitUpdate -f main/common_tests`

2. Within **Eclipse**:
   - Open `MeasureUnitGeneratorTest.java`, find the `generateUnitTestsUpdate` method
    and run it by clicking on the green play button on menu bar. \
    Choose "JUnit Test" if asked. \
    This will not generate the update, but it will run the test and create a "Run Configuration". \
    Open it (Main menu -- "Run" -- "Run Configurations"), select the one named
    `MeasureUnitGeneratorTest.generateUnitTestsUpdate`, go to the "Arguments" tab and add
    `-DgenerateMeasureUnitUpdate` to the "VM Arguments" text area.

Both methods will generate files in the `icu4j/main/common_tests/target/` folder. \
The file names and the logging to the standard output will guide you.

It currently looks something like this:
```
Copy the generated code fragments from / to
    /some/absolute/path/icu4j/main/common_tests/target/MeasureUnit.java \
    /some/absolute/path/icu4j/main/core/src/main/java/com/ibm/icu/util/MeasureUnit.java

Copy the generated code fragments from / to
    /some/absolute/path/icu4j/main/common_tests/target/MeasureUnitCompatibilityTest.java \
    /some/absolute/path/icu4j/main/common_tests/src/test/java/com/ibm/icu/dev/test/format/MeasureUnitCompatibilityTest.java

Copy the generated code fragments from / to
    /some/absolute/path/icu4j/main/common_tests/target/measunit.h \
    /some/absolute/path/icu4c/source/i18n/unicode/measunit.h

Copy the generated code fragments from / to
    /some/absolute/path/icu4j/main/common_tests/target/measunit.cpp \
    /some/absolute/path/icu4c/source/i18n/measunit.cpp

Copy the generated code fragments from / to
    /some/absolute/path/icu4j/main/common_tests/target/measfmttest.cpp \
    /some/absolute/path/icu4c/source/test/intltest/measfmttest.cpp

Copy the generated code fragments from / to
    /some/absolute/path/icu4j/main/common_tests/target/MeasureUnitGeneratorTest.java \
    /some/absolute/path/icu4j/main/common_tests/src/test/java/com/ibm/icu/dev/test/format/MeasureUnitGeneratorTest.java
```

## Copy the generated code

Some kind of diff tool or editor (for example `vi -d`) works nicely.

Look for lines containing `// Start generated ...` and `// End generated ...`.
These lines exist in both the original files, and the generated one. \
Replace all the generated code in between with the contents of the clipboard.

If the generated code has no `// Start` ... `// End ...` pair then the new
code should be appended at some fixed place (details below).

* **`MeasureUnit.java`:** replace range.
* **`MeasureUnitCompatibilityTest.java`:** append the new generated method at the end. \
  It is named something like `TestCompatible<version>()`. \
  If it already exists from an earlier integration in this release, replace it. \
  If the list of constants didn't change since the previous `TestCompatible` method,
  the new method is the same as that one, and you don't need to add it.
* **`measunit.h`:** replace range.
* **`measunit.cpp`:** replace range.
* **`measfmttest.cpp`:** the new `TestCompatible<version>()` method goes in three places. \
  Replace or skip it in the same cases as for `MeasureUnitCompatibilityTest.java`.
  * The declaration in the `MeasureFormatTest` class definition, after the last
    `void TestCompatible<version>();` line.
  * A `TESTCASE_AUTO(TestCompatible<version>);` line in `runIndexedTest()`,
    after the last `TESTCASE_AUTO(TestCompatible...)` line.
    Without it the test is compiled but never runs.
  * The method itself, as generated, after the last
    `MeasureFormatTest::TestCompatible<version>()` method.
* **`MeasureUnitGeneratorTest.java`:** append the new pairs of measure + version at
  the end of the `JAVA_VERSIONS` structure. \
  Don't add them if they already exist.

The generated Java code is not always formatted the way the ICU4J style check
expects, so format it before you commit:

```sh
cd {icuRoot}/icu4j
mvn spotless:apply
```

## Run tests for both `icu4c` and `icu4j`

For ICU4J, install the changed `core` module first, then run the measure unit tests:

```sh
cd {icuRoot}/icu4j
mvn install -DskipTests -DskipITs
mvn install -pl main/common_tests -Dtest=MeasureUnitTest,MeasureUnitCompatibilityTest
```

For ICU4C, rebuild and run the `MeasureFormatTest` tests from a configured build:

```sh
cd {icuRoot}/icu4c/source
make -j
make -C test/intltest check INTLTEST_OPTS=format/MeasureFormatTest
```

Then run the full test suites (`mvn install` in `icu4j`, `make check` in
`icu4c/source`).

## Updating `units.txt` and `unitConstants`

The standard CLDR-to-ICU process is used to update ICU's resource files (see
[CLDR-ICU integration](../../cldr-icu.md)).
CLDR's units.xml defines conversion rates in terms of some constants defined in
`unitConstants`.

For efficiency and simplicity, ICU does not read `unitConstants` from the
resource file. If any new constants are added, some code changes would be
needed. This would be caught by `testUnitConstantFreshness` unit test in
`units_test.cpp`.

They are hard-coded:

* Java: `UnitsConverter.java` (in `com.ibm.icu.impl.units`) has the constant
  names in `UnitsConverter.Factor.addEntity()` and constant values in
  `UnitsConverter.Factor.getConversionRate()`.
* C++: `units_converter.cpp` has the constant names in
  `addSingleFactorConstant()`, with the constant values in `double
  constantsValues[]` in the `units_converter.h` header file.
